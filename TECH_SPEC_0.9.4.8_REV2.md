## P0-1. Заказ становится PACKED без списания

Это главный дефект. Причина найдена точно.

**Цепочка вызовов:**

`marketplaces.py:5310` `wb_scan_chz`
→ `marketplaces.py:1343` `_consume_picking_reservation_strict`
→ `stock_reservations.py:867` `consume_order_reservation`

**Корень — первая строка `consume_order_reservation`:**

```python
def consume_order_reservation(db, order, *, note="WB_PACKED"):
    """0.9.0 final FBS write-off: RESERVED -> physically shipped, exactly once."""
    if not order.last_picking_list_id:
        return {"changed": False, "reason": "no_picking_list"}
```

Если у заказа нет привязки к сборочному листу, списание не выполняется вообще. Функция возвращает `changed: False`.

**Усилитель — `_consume_picking_reservation_strict` (`marketplaces.py:1343`):**

```python
def _consume_picking_reservation_strict(db, order, reason):
    result = consume_order_reservation(db, order, note=reason)
    if result.get("changed"):
        _event(db, order, "PICKING_RESERVATION_CONSUMED", value=reason, data=result)
    return result
```

Функция названа `strict`, но при `changed: False` не делает ничего: ни исключения, ни события, ни лога. Возвращаемое значение в `wb_scan_chz` не проверяется.

**Итог.** Управление идёт дальше, `wb_scan_chz` выставляет `order.local_status = "PACKED"` (строка 5365) и коммитит. Заказ упакован, товар не списан, остаток завышен. Молча.

Отдельно: `consume_order_reservation` возвращает `changed: False` ещё по четырём причинам — `no_reservation`, `already_consumed`, `status_*`, и все они обрабатываются так же, то есть никак.

Само ядро списания (`consume_marketplace_reservation` в `stock_core_v2_service.py`) написано корректно: берёт блокировку строки, проверяет резерв, при его отсутствии бросает `HTTPException(409, "Резерв Stock Core v2 отсутствует")`, использует идемпотентный ключ. **Его менять не нужно.** Дефект целиком в цепочке проверок перед ним.

**Что сделать.**

1. Добавить в `_consume_picking_reservation_strict` параметр `require: bool = True`. При `require=True` и `changed: False` поднимать `HTTPException(409)` с текстом для оператора, зависящим от `reason`:
   - `no_picking_list` → «Заказ не проходил через сборочный лист. Товар не зарезервирован, упаковать нельзя.»
   - `no_reservation` → «Резерв по заказу не найден. Обратитесь к старшему смены.»
   - `already_consumed` → не ошибка, идемпотентный повтор, вернуть успех.
   - прочее → «Списание невозможно: {reason}».
2. При любом `changed: False` писать `logger.error` с `order_id`, `reason`, `result` и создавать событие `PACKED_WITHOUT_WRITE_OFF`.
3. В `wb_scan_chz` вызывать с `require=True`. Проверку разместить **до** записи `local_status = "PACKED"`, чтобы заказ не менял статус при отказе.
4. Пройти по остальным вызовам `_consume_picking_reservation_strict`. Для путей сверки и восстановления (`WB_PACKED_PRINT_QUEUE_RECONCILE` в `_schedule_wb_auto_label_background` и в ручной печати) оставить `require=False`, логирование и событие сохранить.
5. Добавить `GET /marketplaces/wb/orders/packed-without-writeoff`: заказы со статусом `PACKED`, у которых нет события `PICKING_RESERVATION_CONSUMED`. С количеством и суммарным объёмом товара.

**Критерий приёмки.** Через `wb_scan_chz` заказ не может стать `PACKED` без успешного потребления резерва. Попытка упаковать незарезервированный товар возвращает оператору 409 с понятным текстом. Повторное сканирование того же ЧЗ остаётся идемпотентным и не ломается.

**Не трогать:** `consume_marketplace_reservation`, `reconcile_stock_bucket`, `execute_operation`, схему `fc_stock_reservations`, FIFO.

## P0-2. Пул соединений настраивается патчем приватных атрибутов

**Файлы:** `database.py`, `db_pool_tuning.py`, `main.py:299`

**Текущее состояние.** В `database.py` пул не настроен:

```python
engine = create_engine(settings.database_url, pool_pre_ping=True)
```

Дефолты SQLAlchemy: `pool_size=5`, `max_overflow=10`, `pool_timeout=30`.

Компенсируется это на старте в `tune_db_pool` (`db_pool_tuning.py`), который правит уже созданный пул через приватные атрибуты:

```python
q.maxsize = pool_size
pool._max_overflow = max_overflow
pool._timeout = float(timeout)
pool._recycle = recycle
pool._pre_ping = True
pool.dispose()
```

Значения по умолчанию — 20 + 20 соединений, таймаут 5 секунд.

**Проблемы.**

1. Опора на приватный API SQLAlchemy (`_pool`, `_max_overflow`, `_timeout`, `_recycle`, `_pre_ping`). Любое обновление библиотеки ломает это молча — атрибута просто не окажется, `hasattr` вернёт `False`, тюнинг не применится, и приложение вернётся к пулу на 15 соединений с 30-секундным ожиданием. Ровно наблюдаемый симптом 1.
2. Вызов обёрнут в общий `try/except` в `reliability_startup` (`main.py:296-315`) вместе с пятью другими операциями. При исключении печатается `FulfillCore reliability schema warning` и приложение стартует с ненастроенным пулом. Отказ никак не выделен.
3. `pool.dispose()` вызывается, пока соединение стартовой сессии `db` ещё выдано из этого пула. Это портит учёт `_overflow`.
4. Параметры читаются напрямую из `os.getenv` (`FC_DB_POOL_SIZE` и другие), минуя `Settings`. В `config.py` их нет, поэтому они не документированы и не валидируются.

**Что сделать.**

1. Перенести параметры в `config.py` как поля `Settings`: `db_pool_size: int = 20`, `db_max_overflow: int = 20`, `db_pool_timeout: int = 5`, `db_pool_recycle: int = 900`.
2. Задать их в `create_engine` в `database.py` штатным путём.
3. `tune_db_pool` удалить или свести к чтению состояния. Патч приватных атрибутов убрать полностью.
4. В `reliability_startup` разнести операции по отдельным `try` с индивидуальными сообщениями, чтобы отказ одной не скрывал остальные.
5. `db_pool_status` оставить — эндпоинт `/health/db-pool` полезен.

**Критерий приёмки.** `GET /health/db-pool` под авторизованной сессией показывает `size=20`, `max_overflow=20`, `timeout_seconds=5`. Значения выставлены в `create_engine`, а не патчем. При обновлении SQLAlchemy настройки не теряются.

**Диагностика перед правкой.** Присланная диагностика не собралась, команды были некорректны. Правильные:

```bash
docker logs fulfillcore-api-1 2>&1 | grep -E "DB pool tuning|reliability schema warning"

docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -P pager=off -c \
 "SELECT state, count(*), max(now()-xact_start) AS longest FROM pg_stat_activity WHERE datname=current_database() GROUP BY state;"

docker compose exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -P pager=off -c \
 "\d marketplace_order_events"
```

Первая команда — ключевая: она покажет, отработал тюнинг пула или упал. От её вывода зависит, объясняет ли пул симптом 1.

## P0-3. Auth-middleware удерживает второе соединение весь запрос

**Файл:** `main.py`, `single_profile_auth`, строки 137–205

```python
generator = get_db()
db = next(generator)
try:
    commercial = commercial_session_from_request(request, db)
    ...
    response = await call_next(request)   # 183
    ...
finally:
    generator.close()                      # 204
```

Сессия живёт всё время работы основного эндпоинта, который сам берёт соединение через `Depends(get_db)`. Один HTTP-запрос занимает до двух соединений вместо одного. Барьер `AUTH TX BARRIER` (строки 173–181) закрывает транзакцию, но на строках 192–193 соединение берётся снова уже после `call_next`.

Путь super-admin (строки 130–134) соединение не открывает — верно, не менять.

**Что сделать.** Разделить на две короткоживущие сессии: первая только для `commercial_session_from_request`, закрывается до `await call_next`; вторая открывается лениво лишь в ветке `link_resource_to_tenant`, сразу коммитится и закрывается. Данные из `commercial` копировать в обычные Python-объекты, ORM-объекты за пределы сессии не выносить.

## P0-4. Печать не доходит до принтера: 0.9.4.7 отменяет задание и не создаёт замену

**Симптом 4: печать не идёт на принтер.** Регрессия введена самим релизом 0.9.4.7.

**Файл:** `marketplaces.py`, `wb_queue_order_label` (6533), ветка `auto_after_chz`

Порядок действий в текущем коде:

```python
old_jobs = db.execute(select(PrintJob).where(
    PrintJob.object_type == "MARKETPLACE_ORDER",
    PrintJob.object_id == str(order.id),
    PrintJob.document_type == "WB_ORDER_LABEL",
    PrintJob.status == "QUEUED",
)).scalars().all()
for old_job in old_jobs:
    old_job.status = "CANCELLED"
    old_job.error_message = "Отменено 0.9.4.7: заменено единственной фоновой автопечатью"
...
order.raw_data = raw          # маркер _fc_auto_wb_label_pending
db.commit()                   # отмена заданий зафиксирована
scheduled = _schedule_wb_auto_label_background(...)
return {"ok": True, "background_pending": True, "print_job_id": None}
```

Существующие задания печати отменяются и коммитятся **до** того, как фоновый воркер создаст замену. Если воркер не доходит до `queue_print_job` — а он не доходит на всех путях из P1-2: WB не отдал стикер, `worker_busy`, `chz_changed`, `cancelled`, исключение в `_wb_sticker_bytes_without_db` — то нового задания нет, а старое уже отменено. На принтер не уходит ничего.

Дальше маркер `_fc_auto_wb_label_pending` остаётся висеть (P1-2), и следующие 120 секунд повторные запросы возвращают `background_pending: true`, не создавая задание. Фронтенд при этом показывает оператору успешный тост. Отказ полностью бесшумный.

**Что сделать.**

1. Никогда не отменять существующее задание до того, как новое реально поставлено в очередь. Правильный порядок: воркер получил стикер → создал новое задание → в той же транзакции отменил предыдущие `QUEUED` для этого заказа → коммит.
2. Если воркер завершается без задания печати, восстанавливать статус ранее отменённых заданий обратно в `QUEUED`.
3. Исправить P1-2 (снятие маркера) — без этого пункт не закрывается, оператор не сможет повторить печать вручную.

**Диагностика, показывает масштаб немедленно:**

```sql
SELECT status, count(*) FROM print_jobs
WHERE document_type='WB_ORDER_LABEL' AND created_at > now() - interval '7 days'
GROUP BY status;

SELECT count(*) FROM print_jobs
WHERE status='CANCELLED' AND error_message LIKE 'Отменено 0.9.4.7%';
```

Второй запрос напрямую считает потерянные этикетки.

## P0-5. Опрос очереди печати блокирует и выгружает всю очередь целиком

**Файл:** `printing.py:43-48`

```python
job = db.execute(
    select(PrintJob)
    .where(PrintJob.station_code == code, PrintJob.status == "QUEUED")
    .order_by(PrintJob.created_at.asc())
    .with_for_update(skip_locked=True)
).scalars().first()
```

`db.execute(...)` выполняет запрос **без `LIMIT`**, а `.first()` отбрасывает лишнее уже на стороне Python. В отличие от `Query.first()`, который добавляет `LIMIT 1` в SQL, здесь этого не происходит.

Последствия на каждый опрос агента:

- `FOR UPDATE SKIP LOCKED` накладывается на **все** строки очереди этой станции, а не на одну;
- из базы вытягиваются все задания вместе с полем `payload` — это бинарные PNG этикеток;
- Print Agent опрашивает несколько раз в секунду, и каждый опрос удерживает соединение из пула.

Дефект самоусиливающийся: чем больше заданий накопилось в `QUEUED` (а из-за P0-4 они копятся), тем тяжелее каждый опрос, тем дольше держится соединение, тем быстрее исчерпывается пул. Это прямой вклад в симптом 1.

**Что сделать.**

1. Добавить `.limit(1)` в запрос.
2. Не выбирать `payload` в запросе поиска: сначала получить `id` задания, затем отдельным `db.get` подтянуть содержимое уже выбранной строки.
3. Ограничить размер выдачи и добавить индекс `(station_code, status, created_at)`, если его нет.

**Дополнительно в том же файле.**

- Строка 53: `db.rollback()` при пустой очереди откатывает и предшествующий `UPDATE` возврата зависших `CLAIMED`-заданий. В текущей логике это не приводит к потере, потому что обновлённые строки видны тому же `SELECT`, но зависимость неочевидная и хрупкая — вынести возврат зависших заданий в отдельную транзакцию, коммитить сразу.
- `print_result` (72) не проверяет, что агент, сообщающий результат, принадлежит той же станции, что и задание. Добавить сверку с `request.state.print_agent_station`.
- `_empty_poll_cache` — модульный словарь. При нескольких воркерах uvicorn у каждого свой, поэтому троттлинг работает неравномерно. Не критично, но зафиксировать в комментарии.

**Проверить отдельно.** Ни один из шести вызовов `queue_print_job` в `marketplaces.py` (строки 3358, 6475, 6625, 6662, 7340, 7496) не пропускает `station_code` через `normalize_station_code`, тогда как `next_print_job` ищет по `station_code.strip().upper()`, а auth-middleware (`main.py:114`) нормализует код задания при восстановлении. Фронтенд сейчас шлёт уже приведённое значение (`app.js:2070`, `.trim().toUpperCase()`), поэтому совпадение достигается случайно. Привести все шесть вызовов к `normalize_station_code` явно, иначе любой вызов из другого клиента или скрипта создаст задание, которое агент никогда не увидит.

## P1-1. Печать сериализована глобальной промис-цепочкой

Тост не должен утверждать, что этикетка напечатана. Добавить индикатор «этикетка в очереди» на карточке заказа, чтобы оператор не жал кнопку повторно.

## P1-5. Возможен пустой ответ при создании клиента или склада

**Файл:** `main.py:186-197`

`response.body_iterator` вычитывается, затем возможное исключение глотается `except Exception: pass`, и `return response` возвращает ответ с уже исчерпанным телом. Клиент получает пустой ответ на успешный запрос.

**Что сделать.** Сначала вычитать тело в переменную, затем в любом случае собрать новый `Response` с этим телом, и только после этого выполнять привязку к тенанту в отдельном `try`. Ошибку логировать.

## P1-6. Блокировка удерживается во время HTTP-вызовов к WB

**Файл:** `marketplaces.py:5156, 5205, 5244, 6150, 7010, 7116, 7158`

Внутри `distributed_lock(db, f"wb-chz-supply:{key}", blocking=True)` выполняются сетевые вызовы: `client.supplies()`, `_wb_add_orders_to_supply`. Ключ блокировки общий для всей поставки, то есть для многих заказов сразу. Пока WB отвечает медленно, все остальные операции по этой поставке ждут. Блокировка блокирующая, без таймаута.

Реализация `distributed_lock` в `runtime_reliability.py` не предоставлена. **Первым делом проверить:** если это `pg_advisory_lock` без таймаута, ожидание неограниченно, и это второй кандидат на объяснение симптома 1.

**Что сделать.** Добавить обязательный таймаут ожидания блокировки (не более 5 секунд) с понятной ошибкой при истечении. Вынести сетевые вызовы за пределы критической секции: под блокировкой держать только чтение и запись кэша, HTTP выполнять снаружи.
